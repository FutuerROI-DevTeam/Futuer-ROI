## Product Overview

| 項目 | 内容 |
| --- | --- |
| Problem | 今日行動しないことによる将来への影響が見えず、「今日はやらなくてもいいか」と判断しやすい |
| Target User | 毎日取り組みたい、量で表せる継続行動を持つ人（英語学習、資格勉強、読書、コーディング学習、毎日の運動など）。MVPは「毎日1回の実行機会がある行動」に限定する |
| Core Value | 自分の記録から、今日やらなかった場合に、自分で決めた努力量への到達がどれくらい後ろへずれるかを見える化する |
| Hero Copy | **今日サボると、ゴールは何日遠ざかる？** |
| 意味の範囲 | g50は今日休んだ後の再開待ち中央値。同じ継続傾向・設定量と、再開後の経路を時間シフトして共有するモデルでは、累積努力量への到達が遅れる日数の中央値でもある。完了日中央値どうしの差・実際の因果効果・成果そのものの達成日は示さない |
| Need Validation | 未検証。表示が今日の行動判断に役立つかはProduct Hypothesisとして扱う |

### Future ROIがしないこと

- 成果そのもの（TOEICの点数、体重、合格）の達成日を予測しない。予測対象はユーザーが決めた累積努力量への到達だけ。
- 「サボると雪だるま式に未来が悪化する」とは言わない。
- 因果効果を主張しない。記録から推定した傾向が今後も続くと仮定した計算である。
- 習慣の強さを測定すると主張しない。
- LLMに予測・必要努力量の決定をさせない。

## Core User Flow

1. ユーザーがアカウントを作成してログインする。
2. Goalを作成する（タイトル、単位、投資すると決めた総量、1回の量、記録開始日の前日までに終えた量。初期値0）。
3. 毎日、今日のDONE / SKIPPEDを記録する。昨日が記録開始日以降で未記録なら「昨日はどうでしたか？」で補完できる。今日から記録を始めるGoalでは昨日分を追加せず、翌日に今日の記録漏れを補える。
4. 材料がそろうと、「今日サボると約○日遠ざかる」のモデル上の目安と、設定量で続ける場合の完了見込みを、それぞれの出所・仮定とともに確認できる（不足時はR-06/R-11）。
5. 今日やるかを判断し、DONE / SKIPPEDを記録する。

開始時の質問から仮の見通しを作り、実績で更新する機能Scopeは[R-11で採択済み](#質問から始める見通しr-11)。質問入力の具体Flow・未回答時の条件付き計画との接続はD-26で具体化する。回答状況と採択する表示条件によって値の可否が異なり、全員に仮の予測を常時表示する仕様ではない。

### 時間量の表示と整数分の保持

2026-10-09の[P-18の依頼者判断](#p-18-整数分を保った時間分表示)により、`minutes`の累計・総量・残量は、元の整数分を正確な「時間＋分」で表示する。例えば1240分は20時間40分。入力・API・保存・達成判定・予測は整数分のまま扱い、編集の初期値も保存された分数を使う。小数1桁へ丸めた表示値を計算や保存へ戻さない。日々の量の入力は整数分を維持し、`sessions`（回）は変更しない。

#157（[PR #163](https://github.com/jogi-hack-2026-team/jogi-hack-2026/pull/163)）で画面実装と自動回帰を追加した。確認済みの固定例・実ブラウザの範囲と残る受入確認は[検証記録](changes/issue-157-review-regression.md)に記す。[実装の入口と確認対象](change-map.md#時間量の表示方針121)へ追跡する。`targetDate`や小数時間入力・保存の追加は、この採択に含めない。

### 公開トップと認証後の導線

根拠は [#88の依頼者方針](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/88#issuecomment-5986871503) と [PR #139で公開した追加承認の範囲](https://github.com/jogi-hack-2026-team/jogi-hack-2026/pull/139#issuecomment-6051646660)。今回の最小入口接続と、含めないサンプル予測の扱いは [P-16](#p-16-公開トップからgoalへ進める最小入口接続) に記録する。

公開トップ `/` は、未ログインでも製品の説明と登録・ログインへの入口を表示する。ログイン状態を確認中は「確認中」、ログイン済みならGoal一覧への入口を表示する。トップではGoal・記録を取得しない。

登録・ログイン後は、指定したアプリ内の戻り先があればそこへ戻り、指定がなければ `/goals` を開く。認証画面間の切替でも戻り先を保つ。Goalが0件なら一覧の作成ボタン、既存Goalがあれば一覧の各GoalからTodayへ進める。共通ナビのGoal一覧と、作成・Todayの一覧へ戻る操作で、URLを手入力せず主要Flowを操作できる。Goal一覧・作成・編集・Todayと業務APIは引き続き認証を必須とし、未ログインで保護画面を開いた場合は元のURLを戻り先にしてログインへ送る。

### Today Decision画面の表示仕様

下表は現行の実績由来モードの表示。R-11の回答由来モードを追加するScopeは採択済みだが、具体の表示契約はOPENであり、「あなたの記録から」や実績件数を流用しない。回答由来の注釈・表示可能条件・不足時の文言は下の未決事項で具体化する。今日記録済み（R-07）・達成済み（R-08）の優先は維持し、補助指標は補助指標2だけを表示する（2026-10-08、P-12の改訂）。

| 要素 | 文言 | 値の出どころ |
| --- | --- | --- |
| 見出し | 今日サボると、ゴールは何日遠ざかる？ | P-11/P-12/P-17の既存コピーを保持（P-21のレビュー訂正）。計算式は変更しない |
| 中心指標 | ゴールが遠ざかる日数（目安）：**約{g50}日** | [Prediction Engine](architecture.md#prediction-engine)の`coreMetric.g50` |
| 中心指標の注釈 | あなたの記録から推定した「休んだ後の再開傾向」をもとに計算しています。今日休んだ場合、次に再開するまでの日数の中央値です。同じ継続傾向と設定量で続け、再開後に同じ道をたどるモデルでは、完了が遅れる日数の中央値とも解釈できます。完了日の中央値どうしの差や、実際の因果効果を表すものではなく、将来を保証するものではありません。 | — |
| 補助指標1 | 表示しない（2026-10-08、P-12の改訂）。旧文言「休んだ翌日にやれたのは **{nSD+nSS}回中{nSD}回**」 | `observations`（Engineは引き続き返すが、画面には出さない） |
| 補助指標2 | 設定量（{1回の量}）で続ける場合：**{p50の週}ごろ**（10回中8回は{p80の週}まで） | `completion`。日付はその日を含む週の月曜日で表示する。P50が`null`の場合は「約3年以内の目安なし」 |
| 補助指標2の注釈 | 完了の目安は、同じ記録から推定した継続傾向をもとに計算した見込みです。 | — |
| データ不足（中心指標） | まだ「休んだ翌日」の記録がありません。記録がたまると、あなたの再開傾向から推定します。 | `coreMetric.status = insufficient` |
| データ不足（完了の目安） | 「やった翌日」と「休んだ翌日」の記録がそれぞれたまると、完了の目安を表示します。 | `completion.status = insufficient` |

上表の「約3年以内の目安なし」はP50が`null`のときの文言とする。P80が`null`のときは「10回中8回の完了時期の目安は、計算範囲の約3年以内には収まりません。」と表示し、日付の軸の読み上げも同じ意味にそろえる。これは80%到達の目安が計算上限1095日以内に見つからないという意味であり、「80%が期間外」や将来の完了不能を意味しない。P50が有限ならその週の目安を保持し、両方`null`とは分ける。範囲内・範囲外はEngineの日数・`null`から区別し、週のラベルから確率や範囲を逆算しない。H日目に到達した分位点・0日は有限として扱う。達成済み・材料不足・条件付き計画の状態優先と、質問／記録の出所・注釈は変更しない（[#154](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/154)）。

P50が`null`の補足は「約3年の計算範囲内で、完了する見込みが50%（半分）に届かないためです。材料不足や、将来も完了できないという意味ではありません。」、P50有限／P80が`null`の補足は「約3年の計算範囲内で、完了する見込みが80%に届かないためです。材料不足や、将来も完了できないという意味ではありません。」とする。どちらも材料がある`completion.status = available`の説明で、材料不足の`insufficient`や設定量による残り回数の計画とは区別する。質問由来にも同じ説明を使い、出所の注釈は別に保持する。数値未収束を検査する契約はなく、その理由を追加しない（[#198](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/198)）。

中心指標を「シミュレーション」と呼ばない（閉形式の計算であるため）。「今日やれば○日早くなる」と断定する表現、損失を強調して休んだ日を責める表現を使わない。

操作ボタンの文言は「やった」「今日は休む」。P-11/P-12/P-17の問いと中心ラベルを保持し、P-21のレビュー訂正でモデル上の遅れと完了日中央値どうしの差を区別する。未保存入力の効果へ読み替えず、I-12の本人UX確認は完了扱いにしない。

### P-14 記録のルール

以下の「担当不足」「実装が別途必要」「文言未実装・契約未決」は判断時点の記録として読む。2026-10-09の基準mainでは今日・昨日のAPIと画面があり、`recordStartDate`は[Goal DTO](../apps/api/src/contracts/goal.ts)から返され、[GoalFormPage](../apps/web/src/features/goals/GoalFormPage.tsx)が初期量の説明へ渡す。現行の経路・検証記録と残る受入条件は[対応表](change-map.md#アプリの仕様と実装)で確認する。ここに残した当時の文言案を、そのまま現行画面の全文とは扱わない。

2026-09-30 / **DECIDED（依頼者判断）** / 記録はDONE / SKIPPEDの2値。記録のない日はUNKNOWNとして扱い、SKIPPEDとみなさない。記録できるのは今日と昨日だけ（昨日は補完用）。記録が1件でもあるGoalはtimezoneと記録開始前の量を変更できない（過去の日付の基準と予測の意味を変えないため）。やらなかった日ほど記録されない偏りは統計的に補正せず、前日補完のUXで減らす。偏りはKnown Limitationとして[Architecture](architecture.md#known-limitations)に記録する。

2026-10-03 / **依頼者指示による明確化（文書反映、実装未検証）** / 今日・昨日の範囲を維持し、昨日の誤記も訂正できるものとして上記の「補完用」を明確化する。以下は記録の意味と理由であり、新しい画面の実装完了を示さない。

- UNKNOWNは「分からない」であり、休んだ証拠ではない。未記録を自動でSKIPPEDにせず、「後で答える」でも行を作らない。記録済みをUNKNOWNへ戻す削除・取消操作は未採択。
- 記録は「いつ入力したか」ではなく「いつ行動したか」に付く。今日入力する昨日分は昨日の記録として明示し、同じGoal・行動日への保存は既存の記録を置き換える。入力のたびに実績を加算すると、訂正・再送で量が増えてしまうため、現在の記録から再計算する。
- 記録開始日以降の昨日のDONEは実際の量を確認・訂正できる。`sessionAmount`は入力の既定値と将来計算用の量であり、変更しても保存済みのDONE量を書き換えない。初期進捗との境界は下の承認済み追補に従う。
- 今日・昨日だけに限る理由は、MVPのMust完成に向けて入力・訂正・日付境界の実装と確認を抑え、直近の記録忘れと誤記に対応するため。科学的に最適な日数という根拠はない。7日間など長い範囲の編集は、記憶違い・訂正負担・再計算への影響を比較する将来候補であり、今回は採用しない。
- 前日補完は記録忘れを減らす狙いで、効果は未検証。UNKNOWNを含むペアを除いても、休んだ日ほど未記録になる偏りは解消しない。予測は記録されたデータに基づく見立てである（[限界と研究の位置づけ](architecture.md#known-limitations)）。

現在の分担は[#77](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/77)が今日・昨日のPUT上書き、[#79](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/79)が今日の変更と再取得、[#80](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/80)が昨日未記録時の問いかけ。記録済みの昨日を訂正する入口・担当は不足しているため、3 Issue間で調整する。未記録時だけの問いかけを訂正UIとして兼用しない。画面・APIの実装と統合は別途必要で、既存のHard依存を解除しない。[受入確認](architecture.md#記録補完訂正の受入確認)へ追跡する。

### P-18 整数分を保った時間＋分表示

2026-10-09 / **DECIDED（依頼者判断、時間量の表示・整数分保持に限定）** / [#121の採択記録](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/121#issuecomment-6072747976)に基づき、累計・総量・残量の表示を正確な時間＋分にする。依頼者は、時間の制約から仕様文書へのチーム承諾待ちを追加せず、この方針で進め、理由・他案・トレードオフを記録するよう指示した。3人全員の合意を示すものではない。[従前のC案比較](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/121#issuecomment-6064357029)からの限定採択であり、C案全体、`targetDate`、小数時間入力・保存を一括採択しない。#121の既存のB案・分布表現のレビュー完了条件も、この記録だけで満たした扱いにしない。

**理由：** 長いGoalで時間の規模と1分単位の累計・残量を同時に示し、既存の[整数分のデータ契約](architecture.md#data-model)を維持するため。1240分は20時間40分であり、小数1桁の20.7時間を分へ換算すると1242分になる。3000分のGoalで実績2999分なら、1分残って未達成だが、両者は50.0時間、残量は0.0時間に丸められる。表示の丸めで到達・残量を誤認させないことを優先する。読み取りやすさの改善効果を実測したという根拠はなく、狭い画面での折返しや理解確認は実装後に残る。

| 選択肢 | 利点 | 今回の判断・トレードオフ |
| --- | --- | --- |
| 分だけで表示 | 正確で、既存表示からの変更が少ない | 長い総量が大きな数字になる。整数分の入力は維持するが、累計・総量・残量の主表示には採用しない |
| 小数1桁の時間で表示 | 短く時間の規模を示せる | 分単位の差が隠れるため、上記3量の主表示には採用しない。丸めた値は達成判定・予測・編集に使用しない |
| 正確な時間＋分で表示 | 時間の規模と分単位の差を保ち、保存契約を変えずに済む | 採用。文字数が増えるため、狭い画面での折返し・読み取りやすさを確認する |
| 小数時間の入力・保存へ変更 | 時間単位で直接入力できる | 変換・精度・API／DB契約の検討が必要。今回採用せず、整数分の入力・保存を維持する |

**実装の受入条件：** 表示だけを整数分から変換し、時間は整数商、分は60で割った余りを用いる。0の例は累計・残量の表示であり、総量・1回量の正数制約を変更しない。

| 元の分数 | 正確な時間＋分の値 |
| --- | --- |
| 0 | 0時間0分 |
| 1 | 0時間1分 |
| 59 | 0時間59分 |
| 60 | 1時間0分 |
| 61 | 1時間1分 |
| 1240 | 20時間40分 |
| 2999（総量3000に対する実績） | 49時間59分。総量50時間0分、残り0時間1分で未達成 |

- 上の固定例を累計・総量・残量の表示で確認し、1分が小数丸めで隠れないことを確認する。0の単位を省略する場合も、値と意味を変えない。
- 達成判定と[予測入力](architecture.md#prediction-engine)は元の整数分を使用する。表示文字列から逆算せず、表示を追加しても同じ整数入力・結果を維持する。
- 編集の初期値を元の分数から作り、未変更保存で元の値を維持する。日々の量の入力・保存も整数分のまま、回数Goalの入力・表示・計算も維持する。
- 狭い画面で累計・総量・残量の区別と1分の差が読めることを機能QAで確認する。初見の理解確認は後続とし、文書へのチーム承諾待ちは新たに設けない。

P-18採択時の文書反映自体は実装完了を意味しない。その後の#157で累計・総量・残量の画面実装、固定例・編集の整数分保持の自動回帰を追加した。実ブラウザの確認範囲・未確認事項は[検証記録](changes/issue-157-review-regression.md)、関連する表示・編集箇所は[変更対応表](change-map.md#時間量の表示方針121)を参照する。

### P-20 量の意味と保存操作の保全（#148）

2026-10-09 / **依頼者の実装指示・チームレビュー対象** / [Issue #148](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/148)のphase1を対象とする。過去の10分を10回へ読み替えない。過去DONEを示す永続marker、または現在の正の初期量がある場合は単位変更を拒否し、名称などを一緒に変更しても全体を保存しない。DONEをSKIPPEDへ訂正してもmarkerは消さない。新規のSKIP-onlyは単位変更可能。移行前のログはSKIP-onlyも保守的に固定する副作用を許容する。ログなし・初期量のみなら初期量を0にする保存の後、別の保存で単位変更できる。同時変更は旧状態で拒否する。
