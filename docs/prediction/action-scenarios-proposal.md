## 目的と利用例

Future ROIの「今日の行動が未来にどうつながるかを見せる」という方向性を保ちながら、未来の数日間にやる／休むを仮置きして比べられるようにする案。今日だけでなく「今日は休んで明日やる」「数日続ける」を考えている人が、**同じGoal・同じ実記録を前提にした累積努力量への到達見通し**を並べて読めるようにしたい。

比較対象はユーザーが決めた分・回の累積努力量であり、成果、資格合格、健康状態の予測ではない。指定した行動を実行し、指定していない日には記録から推定した行動傾向が続くと仮定した試算。個人への因果効果や「今日やれば何日得する」という保証を示す機能にはしない。

たとえば、今日が未記録で、到達見通しを出せるだけの実記録がある場合に、次の候補を比較する。

| 候補 | 今日 | 明日 | 明後日 | その後 |
| --- | --- | --- | --- | --- |
| 今日1回取り組む | やる | 未指定 | 未指定 | 記録から推定した傾向に従う |
| 今日は休み、明日取り組む | 休む | やる | 未指定 | 同上 |
| 今日から3日間取り組む | やる | やる | やる | 同上 |

この表の「やる」は、初期案ではGoalの`sessionAmount`（1回の量）を1日1回分だけ加える。「休む」はその日の量を加えない。「未指定」は「休む」「記録なし（UNKNOWN）」ではなく、将来の行動を固定しないという意味。モデルが直前の状態に応じてDONE／SKIPPEDの可能性を計算する。

**「今日1回取り組む」は、明日以降ずっと休む指定ではない。** 「今日から3日間取り組む」も、その後ずっと続ける指定ではない。仮置きは実記録へ保存せず、約束や実行済みの記録として扱わない。

## 定型3候補で増える情報と計算の関係

この3候補は、今日から連続した日を指定し、その後をすべて未指定にする形である。M1では、指定後の未来は「最後の指定日のやる／休む」と「残り何回やれば届くか」で決まる。**この初期3例のために、日別指定DPを新設する必要はない。** 既存の完了DPへ残り回数を渡し、今日からのずれを足す方法を、最小の計算候補とする。任意の日を指定し、間に未指定の日を挟む一般化は別の拡張案である。

記号を揃える。`N`は今日の仮置きを加える前に必要な回数で、残り努力量を`sessionAmount`で割って切り上げた数。実績未到達なので`N ≥ 1`とする。今日は0日目。`θ = (a, b)`は継続・再開の確率の組で、各候補に同じ値を渡す。`U_D(r; θ)`は「直前にやった状態から、翌日以降にあと`r`回やるまでの日数」の分布で、`r = 0`なら0日。既存DPが計算する部分に当たる。

| 候補 | 今日からの到達日数の分布 | 新しく分かること・限界 |
| --- | --- | --- |
| 1：今日1回、以後未指定 | `T₁ = U_D(N − 1; θ)` | 現行の今日DONEの完了の目安そのもの |
| 2：今日休み、明日1回、以後未指定 | `T₂ = 1 + U_D(N − 1; θ)` | 同じ前提なら候補1をちょうど1日後ろへずらすだけ。「明日必ずやる」という指定が再開待ちを取り除く |
| 3：今日から3日DONE、以後未指定 | `N ≥ 3`なら`T₃ = 2 + U_D(N − 3; θ)`。`N = 1, 2`ならそれぞれ0日、1日 | 候補1より残り回数を2回減らし、開始を2日ずらした既存DP。必要量に届いた後の指定日は到達日を遅らせない |

同じ事後パラメータの組で平均する場合も、この関係を保つ。打ち切り前の日数分布では候補2は候補1の1日シフトで、利用者の記録に依存しない。候補3との差はM1の継続・再開傾向には依存するが、新しい行動モデルを学習しているわけではない。既存の値を並べ直すだけで利用価値が増えるとは、現時点では確認できていない。

`H`（今日から計算する日数の上限）で区切るときは、候補2のDPを`H − 1`日、候補3（`N ≥ 3`）のDPを`H − 2`日までとして同じ時間軸に戻す。単に「H日以内に未到達」の箱を1日／2日ずらす計算はしない。たとえば候補2の未到達確率は`P(T₁ > H − 1)`であり、候補1の`P(T₁ > H)`と同一とは限らない。指定中に到達する少量のGoal、期間内に到達しない確率、分位点が期間外になる境界も確認する。

[第二レビューの報告](https://github.com/jogi-hack-2026-team/jogi-hack-2026/pull/93#discussion_r4163300550)では、試作DPと合成の事後分布4種・必要回数30/120/400の12条件（Node v25.8.2、K=200、H=1095）で上の還元を照合し、候補1と3のP50差は1〜4日、P80差は1〜6日だったとされる。`a ~ Beta(16, 7)`、`b ~ Beta(5, 8)`、`needed = 120`の条件でseedを5種変えた例では、候補1のP50が206〜215日に動いた。これは**レビュー担当者の測定報告**であり、使い捨ての照合スクリプトは未共有。本資料の作成者はその測定を再実行しておらず、全履歴・全Goalで差が小さいという証明、本実装の性能、実ユーザーへの有用性の証拠にはしない。

[最新の再レビュー](https://github.com/jogi-hack-2026-team/jogi-hack-2026/pull/93#pullrequestreview-5389097378)では、レビュー担当者がNode v25.8.2で日別指定の総当たりDPを作り直し、試作`completion-dp.mjs`と照合したと報告した。境界の格子（`a, b`各5値、`N = 1..7`、`H = 0..12`、3候補）の6,825比較で差0、事後分布2種×必要回数30/120/400の6条件（K=200、H=1095）で差1.9e−16以下だったとされる。前回の209／210／208日、348／349／344日と上のseed別206〜215日も再現したという。これも**投稿者の測定報告**で、この文書の分離作業では再測定していない。PR #93の文書へのApproveは、機能採用・技術採択・本実装の保証ではない。

## 中心指標と「明日必ずやる」の前提差

候補2を例に入れた狙いは、「今日は休んで明日やる」と考える人に、その**予定どおり明日必ず実行する条件付き**の到達見通しを見せること。ただし、実際に明日再開できるかを推定した値ではない。中心`g50`は今日休んだ後の再開待ち`G`を記録から推定するため、候補2の前提とは違う。今日休み、明日以降を未指定にする場合は、固定した`θ`の下で既存の`T_skip = T_done + G`が扱う場面になる。事後平均後の中央値同士を足す式ではない。

同じ画面に「休むと約3日遠ざかる」と「明日やれば1日遅れ」を並べると、計算上は条件が違っても、「休んでよい」「明日やれることが確認できた」と読まれる危険がある。候補2を初期範囲から外す案、比較自体を見送る案、別の画面で前提を明示する案も比較する。注釈の候補は「この案は明日必ず取り組む前提です。再開できるかの予測ではありません。中心の数値は、今日休んだ後の再開待ちの目安です。」。配置・注釈で誤読を防げるかは未検証で、候補2を含めるかはチームのProduct判断に残す。

## 想定する画面と操作

既存Today Decisionから開く「数日間の行動を比べる」補助画面またはパネルを候補にする。URL・画面配置は未決定で、上の再検討案の合意が前提。既存の中心指標や注釈を隠したり、記録ボタンを仮置き操作へ変えたりしない。

1. 同じGoalと履歴を対象に、上の3候補を選ぶ。初期案は今日〜明後日の最大3日・最大3候補に絞り、自由な量の入力や長期カレンダーは含めない。
2. どの日を「やる」「休む」に指定し、どの日を未指定にしたかを、比較結果の横でも確認できるようにする。
3. 複数の到達見通しを、同じ開始日・時間軸・尺度で並べる。不確かさも表示し、一つの確定到達日だけを示さない。
4. たとえば中央値と80%点（条件付きの試算で50%／80%がそこまでに到達する日）を示す候補や、分布を図で並べる候補があるが、D-21や補助指標の制限に触れる未採択案。表示方法は再検討案のチーム合意と簡易ユーザー確認で選ぶ。3年以内に到達しない確率も隠さず、到達する場合だけに絞って分布を作り直さない。
5. 注釈は「指定した行動を行い、それ以外の日はこれまでの傾向が続くと仮定した目安です。将来を保証するものではありません。」などを候補にする。

仮置きの変更、読込中、計算失敗、古い結果が残る状態を区別する。変更後の結果ができるまでは前の結果を新しい指定の結果として見せない。比較を閉じても実記録・Goalは変わらない。

## 計算方法の候補

既存の**DP（動的計画法：状態ごとの確率を日ごとに更新して、到達日を求める方法）**の再利用を候補にする。表の定型3候補は上の還元式で計算でき、既存DPの残り回数と開始状態、日数のずれを組み立てる案を先に検討する。**日別指定DPの新設を初期3例の必要条件や工数の前提にしない。** 指定日と未指定日が入り交じる任意日程へ広げる場合のDP拡張は別候補とする。

これは設計候補であり、論文・実運用例や他の方式を精査して「最適」と判断した結果ではない。上の還元とレビュー報告は参照するが、一般日程の方式比較・追加比較の本実装性能は未検証。現行D-22の採用と、この追加案での方式選定を分ける。APIのpath、入出力の型、保存方式はこの資料では確定しない。

1. 同じ時点のGoal・実記録・`today`を比較の共通入力にする。時刻・timezoneの判断はBEが担い、Engineは時計を読まない。取得の整合をどう保証するかは、既存の[未合意の読み取り順](../architecture.md#検証コードとの差分変更案未合意)と合わせて決める。
2. **実記録だけ**から遷移数と事後パラメータ分布を求める。事後分布は「その人の継続・再開の傾向がどの程度ありそうか」を表す。不足データを仮置きで補わない。
3. 各候補で同じ事後分布を使い、DPへ渡す`a`（やった翌日にやる確率）・`b`（休んだ翌日にやる確率）の抽選値の組も共通にする。seed（乱数を再現する初期値）・サンプル数・計算範囲も揃える。別々の抽選によるぶれが、日程の差に見えるのを避ける狙い。
4. 初期3例では、連続した指定期間の実行回数と最後の状態を先に決め、未指定の残り期間だけを既存DPへ渡す。指定期間中に必要量へ届く場合はその日で到達とする。日別の確率更新を追加しない。任意日程へ広げる別案では、指定日のDONE／SKIPPEDへ確率を進め、未指定日に既存M1の遷移を使う方法を候補にできるが、初期3例とは分けて評価する。
5. 今日の実績、仮置きによる量、将来の量を区別して、二重加算せずに到達分布を計算する。仮置きは予測の経路には影響するが、実記録の遷移数や事後分布の更新には使わない。

任意日程へ拡張する別案でも、微小な確率を捨てて分位点を変える計算は行わない。既存DPの刈り込み（到達できない状態の計算を省く工夫）が一般の指定日にも適用できるかは別途検証が必要。初期案では、今日1回だけを指定し、その後を未指定にした候補が、同じ条件で現行の「今日やった場合の完了の目安」と一致することを確認する。

これは日程を変えた**条件付きの計算の比較**である。指定行動をした人の将来の傾向が変わることはモデルに含めず、現実の介入効果が分かったとは言わない。共通パラメータを使っても、モデルの仮定や実記録の偏りは残る。

## 既存の優先規則と初期範囲

[Engineの状態判定順](../architecture.md#状態の判定順)と[Productの表示規則](../product-spec.md#today-decision画面の表示仕様)を維持する。そのうえで、初期案の利用条件を狭くする。

| 状態 | 初期案での扱い |
| --- | --- |
| 実入力が不正 | 比較結果を作らず、既存の入力エラーを維持する |
| 実績が総量に到達済み | 達成表示を優先し、追加比較を出さない。仮置きで実際の達成状態を戻さない |
| 今日が記録済み | 初期案では追加比較を出さず、実記録と既存の現在状態からの目安を表示する。今日の実行を仮置きで上書きしない。明日以降だけの比較は将来の別判断に残す |
| 完了の目安に必要な遷移が不足 | 追加の到達分布を出さない。DONE起点・SKIPPED起点をそれぞれ1件以上観測する現行条件を維持。中心`g50`だけが表示可能な場合は、その現行表示を妨げない |
| 今日が未記録、未達成、必要な遷移あり | 上の3候補の比較対象にできる案。`sessionAmount`と既存の累積努力量を使う |
| 仮置きでは到達するが、実績は未達成 | 条件付きの到達見通しとしてだけ表示する。実績の達成済み状態へ変更しない |

比較前に実記録が変わったり日付が変わったりした場合、別の履歴・別の「今日」の結果を混ぜない。再計算または結果を無効にする扱いは未決定。

## FE・BE・Engineへの影響

| 分担 | 採用した場合の追加作業候補 | 保持する境界 |
| --- | --- | --- |
| FE | 仮置き日程の選択、共通時間軸の比較、不足・未到達・失敗表示、結果の鮮度と注釈。図の読み方が伝わるかの簡易ユーザー確認 | 予測を独自に計算しない。実記録保存と仮置き操作を分ける |
| BE | 所有者の確認、Goal・履歴・日付を揃えた入力、日別指定の検証、Engine結果の返却、比較中の負荷への対処 | 仮置きをActionLogや学習用履歴へ書かない。既存API契約を流用で変更しない。新しいAPIが必要かは未決定 |
| Engine | 初期3例は共通の事後パラメータと既存DPの入力を組み立て、日数を補正。指定中の到達、未到達、期間上限、不変条件と既存結果の回帰を確認。任意日程のDP拡張は別案 | UI・DB・HTTP・時計から独立。既存`predict`と`g50`の意味を維持する。初期3例のために新しい日別DPが必須とはしない |

複数候補の計算でCPU時間・メモリ・同時実行の負担が増える。単体性能とCRUD・認証の混合負荷を測る必要があるが、測定条件と追加の許容値は採択前に決める。現行T-14の500ms未満を緩めたり、既存Mustの完成度を下げて追加案を優先したりしない。

小さく始める候補は、編集可能なカレンダーを作らず、上の定型候補だけを既存DPから求めること。ただし、差が読めるか、候補2を含めるかも未決定。追加を見送って現行Mustの説明・表示を改善する選択肢もある。Mustを削る提案はしない。比較機能を採用する場合も、自由な量指定、長期日程、仮置きの保存・共有、通知は今回の初期案に含めない。自動再計画・学習テスト特化の案は撤回済みで、この提案には含めない。

scope-guardの観点で、前提を比べる価値、FE/BE/Engineの追加負担、誤読・数値境界・混合負荷のリスク、既存技術採択とMustへの依存、検証負担は上記のとおり整理した。ただし、担当・人日・完了予定を含む**具体的な工数見積もりは未実施**。初期3例を日別DP新設として見積もる前提は取り下げても、画面・入力整合・例外・回帰・ユーザー確認は残る。技術採択とEngine実装が未完了のため、Freezeまでに追加を完成できるとは確認していない。定型／任意日程を分けた見積もりと、Must完成後に実施できるかを採否前の判断材料にする提案であり、Mustの条件やIssueのReadyを変更するものではない。

## 受入条件案（未採択・未検証）

1. 比較する全候補でGoal・実履歴・`today`・事後パラメータ・seed・計算範囲が共通。同じ入力から同じ結果を再現できる。
2. 「今日1回」の明日以降が未指定であることを画面と計算で確認でき、その結果が現行の今日DONEの目安と一致する。
3. 初期3例を`T₁ = U_D(N − 1)`、`T₂ = 1 + U_D(N − 1)`、`T₃ = 2 + U_D(N − 3)`（`N ≥ 3`）の独立した式と照合できる。`N = 1, 2`の指定中の到達、同じHでの未到達も確認する。任意日程へ拡張する場合の指定日／未指定日の遷移と状態の引き継ぎは別に照合する。
4. 仮置きを変更・破棄しても実記録、遷移数、事後分布、実績は変わらない。未来の実ActionLogが作成されない。
5. 不正入力・達成済み・今日記録済み・不足データの優先規則が保たれる。仮置きが実際の達成表示を変えず、今日の量が二重に加算されない。
6. 到達しない確率を残し、H（計算する日数の上限）以内に到達した分だけで分布を正規化しない。既存の確率打ち切り禁止・分位点境界の扱いを守る。
7. 各候補を同じ時間軸・尺度・不確かさの表現で示す。中央値の差を個人への因果効果や保証として説明しない。週の境界・同じ週へ丸まる例・未到達・seedの影響を確認し、表示粒度の変更を精度向上と扱わない。表示採用には上の既存Decisionの再検討案の合意が必要。
8. 所有者・入力の検証、読込中・失敗・日付や実記録更新時の古い結果の扱いを確認できる。
9. 複数候補の計算とAPI混合負荷を合意した条件で測り、既存Mustの応答・性能・数値結果を悪化させない。新しい予算や許容値は別途合意する。
10. 簡易ユーザー確認で「未指定」「仮置き」「目安」「明日必ず実行する条件」と中心`g50`の前提差を理解できるか、差の小さい候補を並べる価値があるかを調べる。利用価値や誤読防止が検証済みだとは現時点で言わない。
